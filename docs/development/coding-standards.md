# 编码规范

本文记录镜造（SceneForge）开发中已确认的基础编码约定。具体工具和检查配置在阶段 0 验证后确定；工具选择不得改变本文约定。

## C++ 标准

- C++ 代码以 ISO C++20 为语言基线，优先使用标准语言和标准库能力。
- 使用 Qt 的模块、类型和 API 属于产品技术路线的一部分，不与遵循标准 C++20 冲突。
- 不依赖编译器专有语言扩展。确有平台相关需求时，应限制在明确的适配边界内，避免扩展泄漏到领域规则和通用业务代码。
- 代码应以标准 C++20 模式构建，并在项目支持的 Windows 编译工具链上验证；不能依赖某一编译器默认开启的非标准行为。

## 注释语言

- 源代码注释和面向开发者的代码说明使用中文。
- 注释应说明意图、约束、非显而易见的原因或需要维护者注意的边界，不重复描述代码本身已经清楚表达的操作。
- 注释应随代码行为变化而同步维护；过期注释视为需要修正的问题。

## 编码与命名

- 源文件统一使用 UTF-8 编码，确保中文注释和文本在不同开发工具中一致显示。
- 类型、函数、变量、常量和文件名遵循项目选定的 C++/Qt 命名风格，并在同一类对象中保持一致。
- 命名风格的具体规则及自动格式化配置在阶段 0 选定，并纳入代码检查；不得在各模块自行采用互不兼容的约定。

## 文件职责

- 每个源文件围绕一个单一、内聚的职责组织，应能用一句话说明其主要责任。
- 不在同一文件中混合彼此独立的领域规则、界面呈现、持久化和外部服务适配职责。
- 当文件因多个独立原因频繁变化、包含不相关的类型或难以单独测试时，应拆分为职责清楚的文件或模块。
- 单一职责不要求机械地每个文件只能包含一个类型；紧密协作且共同表达同一职责的声明可以放在一起。

## 错误与日志

- 错误不得静默忽略；应保留足够的上下文供调用方处理，并向用户提供清楚、可采取行动的反馈。
- 日志用于诊断状态、错误类别和必要的操作上下文，不记录 API 密钥、完整提示词、作品正文或用户媒体内容等敏感信息。
- 处理外部服务、文件和媒体任务时，应明确区分成功、部分成功、失败和取消状态，不以模糊的成功提示掩盖失败项。

## 测试与第三方依赖

- 领域规则和状态转换应有单元测试；存储、媒体处理和外部服务边界应有相应集成测试。
- 测试应覆盖正常结果、失败和取消等重要路径；测试数据应使用许可明确且不含用户隐私的样例。
- 第三方依赖应记录名称、固定版本和许可证；引入或升级依赖前应评估其维护状态、许可证及对应用分发的影响。

## 验收约定

- 新增或修改的代码应符合以上标准；代码评审需关注标准兼容、注释语言、文件职责、错误处理、日志和测试。
- 格式化、静态分析和具体命名配置将在阶段 0 选定并记录；工具尚未确定不免除上述约定。
